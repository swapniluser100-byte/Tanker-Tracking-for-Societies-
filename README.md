# JalSetu — water tanker & supply tracker for housing societies

JalSetu helps a housing society committee in Pune (Wagholi, Hinjewadi, Baner, Kharadi, PCMC…) manage private water tankers when PMC/PCMC supply is irregular:

- **Committee app** (`/app`): dashboard with tank levels, hours of water left, municipal supply reliability, today's tankers, spend vs budget, cost per flat, vendor scorecard, WhatsApp update and monthly CSV report. Includes the booking flow with treasurer approval above a limit.
- **Guard app** (`/guard`): today's expected tankers and a large-button check-in. You enter the vehicle number, the level before and after unloading, and a challan photo (uploaded to R2). The app calculates litres received and flags short deliveries.
- **Resident app** (`/resident`): installable PWA in English and मराठी. It shows whether water is on or off in the resident's wing, today's timings, tankers on the way, their share of the month's cost, notices, and has "no water" / "leakage" reports.
- **Admin console** (`/admin`, super admin and committee admin): society settings, wings and flats (with CSV import), tanks, vendors, sizes and slots, the PMC schedule, users and roles, notification templates, sensor API keys, the audit log and data export.

Everything runs on Cloudflare: one **Worker** (Hono API + React static assets), **D1** (SQLite via Drizzle), **R2** (photos) and **KV** (rate limits).

## Local setup

Requirements: Node 20+ and a Cloudflare account (only needed for deploying; local dev runs fully offline).

```bash
npm install
cp .dev.vars.example .dev.vars        # local secrets (Turnstile test keys, upload signing secret, bootstrap token)
```

### 1. Cloudflare resources (nothing to do)

`wrangler.jsonc` deliberately has **no** D1 or KV IDs. On the first `wrangler deploy`, wrangler creates the D1 database, KV namespace and R2 bucket in the account it deploys to. R2 must be enabled on that account first (Dashboard → R2 → enable). The Worker applies the SQL in `migrations/` on its first request (`src/worker/lib/migrate.ts`), so a fresh deployment needs no separate migration step. Running `wrangler d1 migrations apply` by hand still works, because both share the `d1_migrations` table.

### 2. Apply migrations and seed sample data (local)

```bash
npx wrangler d1 migrations apply jalsetu-db --local
npm run db:seed:local
```

The seed creates **Sai Samarth Residency CHS, Wagholi**: 186 flats in wings A/B/C, four tanks, four vendors, about 470 bookings with check-ins, expenses, 14 days of sensor readings, PMC logs, notices and complaints. It prints the demo logins and a **sensor API key**, which is shown only once.

> ⚠️ The seed SQL deletes existing rows first. Only use it on local/demo databases.

## Creating the first admin

On an empty database (no seed), the app shows a **one-time setup page** at `/setup`. It creates the society and the super admin, then disables itself. In production it requires the `ADMIN_BOOTSTRAP_TOKEN` secret; without that secret, setup is refused.

Or from the command line against a running deployment:

```bash
npm run admin:create -- --url https://jalsetu.<your-subdomain>.workers.dev --name "Aditi Deshpande" --email admin@example.com --username admin --society "My Society CHS" --area Baner --flats 120
```

It asks for the bootstrap token and the password without echoing them. You can also pass them as `JALSETU_BOOTSTRAP_TOKEN` and `JALSETU_ADMIN_PASSWORD` environment variables.

## Secrets

Set these once per environment. They never go in `wrangler.jsonc`:

```bash
npx wrangler secret put TURNSTILE_SECRET_KEY      # from the Cloudflare dashboard → Turnstile
```

```bash
npx wrangler secret put ADMIN_BOOTSTRAP_TOKEN     # random string, used once for first-admin setup
```

Optional: `UPLOAD_SIGNING_SECRET`. If you don't set it, the Worker generates a random signing key and keeps it in D1. Secrets can also be added in the dashboard under Worker → Settings → Variables and Secrets.

Also set `TURNSTILE_SITE_KEY` in `wrangler.jsonc` → `vars` to your real site key. The committed value is Cloudflare's always-pass test key.

## Deploying

Push to GitHub and Cloudflare Workers Builds deploys automatically: it runs `npx wrangler deploy`, which builds the React app through `build.command` in `wrangler.jsonc`. To deploy by hand:

```bash
npm run deploy
```

The Worker name in `wrangler.jsonc` (`tanker-tracking-for-societies`) must match the Worker connected to Workers Builds.

Then open `/setup` (or run `npm run admin:create`) to create the super admin. Add flats via **Admin → Wings & flats → Import CSV** and create users under **Admin → Users & roles**.

## IoT tank sensors

Create a key under **Admin → Sensor API keys** (super admin). The key is shown once and only its SHA-256 hash is stored. Then, from an ESP32 or similar:

```
POST /api/readings
Authorization: Bearer js_live_…
Content-Type: application/json

{ "tank_id": 1, "level_pct": 46.5 }
```

The endpoint also accepts raw ultrasonic distance: `{ "tank_id": 1, "distance_cm": 132, "tank_height_cm": 250, "sensor_offset_cm": 20 }`. It is limited to 12 readings per minute per key. Keys can be restricted to one tank.

## Security model

- **Passwords**: PBKDF2-SHA256 through Web Crypto, 100,000 iterations (the Workers maximum), and a random 16-byte salt per user. Staff passwords are at least 10 characters. Guards and residents may use a 6+ digit PIN instead.
- **Sessions**: a random 32-byte token in an `HttpOnly; Secure; SameSite=Strict` cookie (`__Host-` prefixed on HTTPS). D1 stores only its SHA-256 hash. Sessions last 12 hours and renew while in use. "Log out of all sessions" is under My account, and admins can revoke any session.
- **Login protection**: Turnstile on the login page, an IP rate limit in KV, and a **15-minute account lock after 5 failed attempts** (tracked in D1). Unknown usernames take the same time to reject as wrong passwords.
- **CSRF**: every state-changing request must pass an Origin check and a double-submit token (`X-CSRF-Token` header must match the csrf cookie).
- **Roles**: Hono middleware checks roles on every API route. The UI only hides links. `tests/roles.test.ts` runs the real routers to prove it.
- **Headers**: Content-Security-Policy, `X-Frame-Options: DENY`, `Referrer-Policy`, `nosniff` and HSTS on the API (middleware) and on static files (`public/_headers`).
- **Uploads**: the Worker signs an upload URL bound to the user, key, exact size, type and a 10-minute expiry. The PUT is size-capped at 5 MB, and the file's magic bytes must be JPEG, PNG or WebP. Photos are only served to signed-in committee members and guards.
- **Audit**: every create, update and delete, plus sign-ins, failed logins, locks, exports and key events, is written to `audit_logs` in the same D1 batch as the change. Secrets are redacted.

## Business rules

| Rule | Where |
|---|---|
| Litres received = (after % − before %) × tank capacity | `src/shared/calc.ts` → `litresReceived` |
| Short if the shortfall is more than the tolerance (default 300 L); cost pro-rated to litres received | `evaluateDelivery`, `proRatedCostPaise` |
| Cost per flat = month's tanker spend ÷ flats | `costPerFlatPaise` |
| Hours left = litres ÷ (7-day average daily use ÷ 24) | `hoursLeft`, `avgDailyUseFromReadings` |
| Vendor on-time % and short counts come from check-ins | `src/worker/lib/stats.ts` → `vendorStats` |
| Bookings above the approval limit (default ₹5,000) need treasurer approval | `routes/bookings.ts` |

Money is stored as integer **paise**. Timestamps are UTC ISO strings. Calendar dates and clock times are Asia/Kolkata. Numbers use Indian grouping (`1,50,000 L`, `₹ 25,200`).

> **Note on guard readings:** on a 1,50,000 L sump one 0.5% step equals 750 L, which is more than the 300 L tolerance. The guard screen has ±0.5% buttons but also accepts decimals (e.g. 46.3), and shows how many litres one step represents, so a rounding error isn't recorded as a short delivery.

## Notes and limits

- One deployment serves **one society**. Multi-society hosting would add a `society_id` to each table and scope queries by it.
- Resident/guard login is phone + password/PIN. All credential checks live in `routes/auth.ts`, so an SMS-OTP provider can be added as another endpoint that ends in the same `createSession()` call.
- WhatsApp updates use pre-filled `wa.me` links. Nothing is sent automatically.
